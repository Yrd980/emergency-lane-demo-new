# 高速应急车道检测系统详细设计文档

## 1. 文档目标

本文档在 `docs/requirements.md` 的基础上进一步细化工程设计，目标是让后续实现可以直接拆分为 Android 端、HP 电脑端后端、Web 管理端、模型与数据、测试验收五条开发线。

首版系统聚焦一个完整闭环：

```text
vivo X100 采集画面
    -> 端侧车辆检测
    -> ROI 占用判定
    -> 生成疑似事件
    -> 上传 HP 电脑
    -> 人工复核
    -> 历史留存
```

首版不做执法级自动处罚，不把手机端车牌识别作为必选能力，不依赖手机厂商未公开的 ISP 语义分割能力。

## 3. 子系统边界

### 3.1 Android 端

Android 端只负责“发现和上报疑似事件”，不负责最终判罚。

核心职责：

- 相机预览和帧采集。
- ROI 手动标定。
- 车辆检测模型推理。
- 车辆轻量跟踪。
- ROI 内停留时长判断。
- 证据帧和短视频片段生成。
- 本地事件缓存。
- 上传 HP 电脑。
- 展示运行状态、连接状态和上传状态。

### 3.2 HP 本地后端

后端是首版系统的本地事实源。

核心职责：

- 提供局域网 API。
- 记录手机设备信息。
- 接收事件数据。
- 保存证据文件。
- 对重复上传做幂等处理。
- 保存人工复核结果。
- 为 Web 管理端提供查询接口。

### 3.3 Web 管理端

Web 管理端负责演示和人工复核，不直接参与模型推理。

核心职责：

- 展示事件列表。
- 展示事件详情。
- 展示证据帧和视频片段。
- 支持确认、驳回、备注。
- 支持按状态、时间、设备筛选。
- 展示系统运行状态。

### 3.4 模型与数据

模型与数据线负责把车辆检测模型变成可在 vivo X100 上稳定运行的端侧资产。

核心职责：

- 准备训练和验证数据。
- 训练或微调轻量车辆检测模型。
- 导出端侧模型格式。
- 做 INT8 量化。
- 在 vivo X100 上做帧率、发热、误报验证。

## 4. Android 端详细设计

### 4.1 页面结构

首版 Android App 建议包含 5 个页面：

- 检测首页：实时预览、检测框、ROI、运行状态。
- ROI 标定页：点选多边形、保存、重置。
- 事件队列页：查看本地待上传、上传中、已上传事件。
- 连接设置页：配置 HP 电脑地址、测试连接。
- 系统设置页：配置阈值、帧率、模型版本、存储限制。

### 4.2 检测首页

检测首页是端侧主工作界面。

必须展示：

- 相机实时画面。
- 当前 ROI 多边形。
- 车辆检测框。
- 跟踪 ID。
- 当前 FPS。
- HP 电脑连接状态。
- 当前温度或性能档位。
- 上传队列数量。

必须支持：

- 开始检测。
- 停止检测。
- 进入 ROI 标定。
- 手动触发连接测试。
- 查看最近事件。

### 4.3 ROI 标定页

ROI 标定是手机端方案的关键能力。

交互流程：

```text
进入标定页
    -> 显示实时相机画面
    -> 用户依次点击应急车道边界点
    -> 形成多边形
    -> 用户保存
    -> 系统保存 ROI 配置
    -> 返回检测首页
```

标定规则：

- 至少 4 个点。
- 顶点按用户点击顺序连接。
- 保存前需要显示闭合多边形。
- 支持撤销上一个点。
- 支持清空重画。
- 保存时记录画面尺寸。

ROI 配置字段：

```json
{
  "roi_id": "roi_default",
  "name": "默认应急车道",
  "frame_width": 1280,
  "frame_height": 720,
  "points": [
    {"x": 820, "y": 210},
    {"x": 1260, "y": 240},
    {"x": 1270, "y": 710},
    {"x": 620, "y": 710}
  ],
  "created_at": "2026-05-05T10:00:00+08:00",
  "updated_at": "2026-05-05T10:00:00+08:00"
}
```

### 4.4 相机采集

首版建议使用 CameraX。

采集要求：

- 预览分辨率目标：1280x720。
- 推理输入目标：640x360 或模型实际要求尺寸。
- 推理帧率目标：12-18 FPS。
- 预览帧率可以高于推理帧率。
- 推理线程不能阻塞 UI 线程。
- 采集失败时需要给出可理解错误提示。

性能策略：

- 默认不对每一帧推理。
- 使用固定间隔抽帧。
- 发热时降低推理帧率。
- 上传高峰时避免阻塞推理。

### 4.5 推理模块

推理模块输入相机帧，输出车辆检测框。

输入：

- 图像帧。
- 当前模型配置。
- 推理尺寸。

输出：

```json
{
  "frame_id": 1024,
  "timestamp_ms": 1710000000000,
  "detections": [
    {
      "class_name": "car",
      "confidence": 0.86,
      "box": {
        "x": 120,
        "y": 220,
        "width": 180,
        "height": 90
      }
    }
  ]
}
```

推理要求：

- 支持模型文件本地加载。
- 支持模型版本显示。
- 支持推理失败降级提示。
- 支持置信度阈值配置。
- 支持统计平均推理耗时。

### 4.6 跟踪模块

跟踪模块把连续帧检测结果关联成轨迹。

轨迹字段：

```json
{
  "track_id": "track_42",
  "class_name": "car",
  "first_seen_ms": 1710000000000,
  "last_seen_ms": 1710000001200,
  "last_box": {
    "x": 120,
    "y": 220,
    "width": 180,
    "height": 90
  },
  "confidence": 0.86,
  "inside_roi": true,
  "roi_enter_ms": 1710000000200,
  "roi_duration_ms": 10000
}
```

跟踪要求：

- 同一车辆尽量保持同一个 `track_id`。
- 短时间漏检不立即删除轨迹。
- 丢失超过配置时间后结束轨迹。
- 每条轨迹只生成一个占用事件，避免重复报警。

### 4.7 ROI 判定模块

ROI 判定用于判断车辆是否位于应急车道区域。

判定点建议：

- 首选车辆框底边中心点。
- 可选车辆框中心点。
- 后续可支持车辆框与 ROI 的面积交并比。

首版默认：

```text
判定点 = bbox 底边中心点
如果判定点在 ROI 多边形内，则认为车辆进入应急车道区域
```

该设计比实时车道线分割更稳定，更适合手机端演示和移动拍摄。

### 4.8 事件生成状态机

每条轨迹维护一个事件状态。

```text
outside_roi
    │ 进入 ROI
    ▼
candidate
    │ 持续超过阈值
    ▼
event_created
    │ 证据打包完成
    ▼
queued
    │ 上传成功
    ▼
uploaded
```

状态说明：

- `outside_roi`：车辆不在 ROI 内。
- `candidate`：车辆已进入 ROI，但停留时间不足。
- `event_created`：达到阈值，生成疑似事件。
- `queued`：事件和证据已进入上传队列。
- `uploaded`：HP 电脑端已成功接收。

事件生成规则：

- 默认停留阈值：10 秒。
- 默认检测置信度阈值：0.5。
- 默认轨迹丢失容忍时间：2 秒。
- 单条轨迹同一次进入 ROI 只生成一个事件。
- 事件结束时间可以在车辆离开 ROI 或轨迹结束时确定。

### 4.9 证据生成

每个疑似事件至少包含：

- 事件结构化 JSON。
- 3 张关键帧。
- 1 段短视频片段。

关键帧建议：

- `frame_before`：触发前画面。
- `frame_peak`：车辆在 ROI 内最清晰或置信度最高的画面。
- `frame_after`：触发后画面。

视频片段建议：

- 首版保存触发前 3 秒到触发后 3 秒。
- 如果设备压力较大，可以先只保存关键帧，视频片段作为可选项。

证据叠加信息：

- 检测框。
- ROI 边界。
- 事件 ID。
- 时间戳。
- 设备 ID。
- 置信度。

### 4.10 本地缓存与上传队列

手机端必须支持离线缓存。

上传状态：

- `local_created`：本地生成。
- `queued`：等待上传。
- `uploading`：上传中。
- `uploaded`：上传成功。
- `failed`：上传失败，等待重试。

重试策略：

- 网络不可用时不频繁重试。
- HP 地址不可达时标记失败原因。
- 恢复连接后自动重试。
- 同一事件使用固定 `event_id` 保持幂等。

本地存储限制：

- 支持设置最大缓存空间。
- 超限时优先清理已上传证据。
- 未上传事件不能静默删除。

## 5. HP 后端详细设计

### 5.1 服务职责

HP 后端是本地事实源，首版可以采用单体服务。

服务能力：

- 健康检查。
- 设备注册。
- 设备心跳。
- 事件上传。
- 文件上传。
- 事件查询。
- 事件详情。
- 人工复核。
- 静态证据文件访问。

### 5.2 建议 API

#### 健康检查

```http
GET /api/health
```

响应：

```json
{
  "status": "ok",
  "server_time": "2026-05-05T10:00:00+08:00"
}
```

#### 设备注册

```http
POST /api/devices/register
Content-Type: application/json
```

请求：

```json
{
  "device_id": "vivo_x100_001",
  "device_name": "vivo X100",
  "app_version": "0.1.0",
  "model_version": "yolov8n-int8-20260505"
}
```

响应：

```json
{
  "device_id": "vivo_x100_001",
  "registered": true
}
```

#### 设备心跳

```http
POST /api/devices/heartbeat
Content-Type: application/json
```

请求：

```json
{
  "device_id": "vivo_x100_001",
  "battery_level": 82,
  "thermal_state": "normal",
  "fps": 15.2,
  "pending_upload_count": 2
}
```

#### 事件上传

```http
POST /api/events
Content-Type: application/json
```

请求：

```json
{
  "event_id": "evt_20260505_000001",
  "device_id": "vivo_x100_001",
  "start_time": "2026-05-05T10:00:00+08:00",
  "end_time": "2026-05-05T10:00:12+08:00",
  "duration_seconds": 12,
  "roi_id": "roi_default",
  "track_id": "track_42",
  "vehicle_class": "car",
  "vehicle_box": {
    "x": 120,
    "y": 220,
    "width": 180,
    "height": 90
  },
  "confidence": 0.86,
  "gps_location": {
    "lat": 0.0,
    "lng": 0.0,
    "accuracy_meters": 0.0
  }
}
```

响应：

```json
{
  "event_id": "evt_20260505_000001",
  "accepted": true,
  "duplicate": false
}
```

幂等要求：

- 如果 `event_id` 已存在，返回 `duplicate: true`。
- 重复上传不能覆盖人工复核结果。
- 重复上传可以补齐缺失证据文件，但不能创建第二条事件。

#### 证据文件上传

```http
POST /api/events/{event_id}/evidence
Content-Type: multipart/form-data
```

字段：

- `type`：`frame_before`、`frame_peak`、`frame_after`、`video_clip`。
- `file`：图片或视频文件。

响应：

```json
{
  "event_id": "evt_20260505_000001",
  "type": "frame_peak",
  "stored": true,
  "url": "/evidence/evt_20260505_000001/frame_peak.jpg"
}
```

#### 事件列表

```http
GET /api/events?status=pending&device_id=vivo_x100_001&limit=50&offset=0
```

响应：

```json
{

      "event_id": "evt_20260505_000001",
```

```http
GET /api/events/{event_id}
```

响应包含事件结构化数据、证据文件 URL 和复核信息。


```json

  "review_status": "confirmed",
  "operator_note": "车辆持续占用应急车道，证据清晰。"
```

## 7. 数据流设计

### 7.1 正常在线流程

```text
1. 手机启动 App
2. 手机请求 GET /api/health
3. 手机注册 POST /api/devices/register
4. 手机完成 ROI 标定
5. 手机启动检测
6. 车辆进入 ROI 并超过阈值
7. 手机生成 event_id
8. 手机保存事件和证据到本地
9. 手机上传 POST /api/events
10. 手机上传证据 POST /api/events/{event_id}/evidence
11. HP Web 列表出现待复核事件
12. 复核人员确认或驳回
```

### 7.2 离线补传流程

```text
1. 手机检测到 HP 电脑不可达
2. 新事件保存为 queued 或 failed
3. 手机周期性测试连接
4. 连接恢复
5. 手机按创建时间依次补传事件
6. HP 后端按 event_id 幂等接收
7. 上传成功后手机标记为 uploaded
```

### 7.3 重复上传流程

```text
1. 手机重复上传同一 event_id
2. HP 后端发现 event_id 已存在
3. 后端返回 duplicate: true
4. 后端不创建新事件
5. 后端不覆盖 review_status
6. 手机标记该事件已被服务端接收
```

## 8. 配置项

### 8.1 Android 端配置

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| server_base_url | 手动填写 | HP 后端地址 |
| inference_fps | 15 | 推理目标帧率 |
| confidence_threshold | 0.5 | 检测置信度阈值 |
| occupation_seconds | 10 | 占用触发时长 |
| track_lost_seconds | 2 | 轨迹丢失容忍时间 |
| max_local_storage_mb | 1024 | 本地证据缓存上限 |
| upload_on_wifi_only | false | 是否仅 Wi-Fi 上传 |

## 9. 安全与证据完整性

首版系统用于演示和辅助复核，不宣称满足执法系统全部规范。

首版应做到：

- 每个事件有唯一 `event_id`。
- 每个证据文件记录 SHA-256。
- 上传接口校验基本字段。
- Web 复核操作记录时间。
- 重复上传不覆盖复核结论。

后续可增强：

- 设备密钥。
- 请求签名。
- 证据包签名。
- NTP 时间校准。
- 操作员账号和权限。
- 审计日志。

## 10. 性能与降级策略

### 10.1 Android 端

性能目标：

- 推理稳定 12-18 FPS。
- UI 预览保持流畅。
- 事件生成不阻塞推理。
- 上传不阻塞 UI 和推理线程。

降级策略：

- 温度升高时降低推理 FPS。
- 待上传文件较多时暂停视频片段上传，优先上传事件 JSON 和关键帧。
- 存储空间不足时提示用户清理已上传证据。
- 模型加载失败时禁止启动检测并显示错误。

### 10.2 HP 电脑端

性能目标：

- 本地查询响应足够支撑演示。
- 图片和视频文件按事件目录存储。
- 事件列表分页加载。

降级策略：

- 证据文件缺失时事件仍可展示结构化信息。
- 视频加载失败时仍展示关键帧。
- 数据库写入失败时接口返回明确错误。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 手机发热降频 | FPS 下降，漏检增加 | 动态降频，降低输入尺寸，减少推理帧率 |
| ROI 标定不准 | 误报或漏报 | 标定页提供实时预览和重标定能力 |
| 手机姿态变化 | ROI 失效 | 检测姿态变化并提示重新标定 |
| 模型泛化不足 | 检测效果不稳定 | 使用 vivo X100 实拍数据做微调和验证 |
| 网络不稳定 | 事件无法实时上传 | 本地缓存和恢复补传 |
| 证据文件过大 | 上传慢，占存储 | 首版优先关键帧，视频片段可降级 |
| 重复上传 | 事件重复 | 使用 `event_id` 幂等处理 |
| 复核被覆盖 | 人工结果丢失 | 重复上传不覆盖 `review_status` |
