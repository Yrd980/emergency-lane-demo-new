# 产品需求

## 1. 目标

建设一套用户愿意长期使用的本地应急车道疑似占用检测产品，而不是只能证明链路跑通的 demo。

产品必须让用户在任何页面都知道：

- 当前系统状态是什么。
- 是否有阻断问题。
- 下一步应该做什么。
- 操作是否成功。
- 出错后如何恢复。

## 2. 用户角色

### 现场人员

负责 Android 端接入、相机画面、ROI 标定和检测运行。

核心诉求：

- 快速知道后端地址怎么填。
- 快速知道设备有没有连上。
- 失败时知道检查网络、IP、权限还是模型。

### 复核人员

负责在 Web 端查看证据并确认或驳回事件。

核心诉求：

- 优先看到待处理事件。
- 先看证据，再看字段。
- 复核后有明确成功反馈。
- 能继续处理下一条。

### 维护人员

负责判断系统能否继续运行。

核心诉求：

- 看到设备在线、心跳、上传积压、FPS、温度和模型版本。
- 看到后端、数据库、证据目录是否健康。
- 看到下一步排障建议。

## 3. 核心产品闭环

```text
接入设备
  -> Android 采集和检测
  -> 生成疑似事件
  -> 上传事件和证据
  -> Web 工作台提示待复核
  -> 复核人员查看证据链
  -> 确认或驳回
  -> 系统回到下一条事件或健康监控
```

## 4. 必须具备的产品要求

### 页面层级

- 页面必须有清晰标题、说明和主行动。
- 首页必须显示当前最重要的下一步。
- 事件详情必须以证据链为第一优先级，不以字段表格开场。
- 设备页必须先显示状态和异常，再显示详细字段。

### 状态设计

每个主要页面必须处理：

- loading。
- empty。
- error。
- success 或已完成状态。
- partial data。

不能只显示“加载中”或“暂无数据”，必须给下一步行动。

### Onboarding

必须有接入向导，至少覆盖：

- 后端服务地址。
- Android 端填写地址。
- 设备注册和心跳。
- ROI 标定。
- 生成测试事件。

### 用户反馈

必须提供：

- 复核提交成功反馈。
- 复核失败反馈。
- 复制后端地址反馈。
- 重试反馈。
- 设置保存反馈。
- 危险或不可逆操作的确认。

### Mobile

Web 必须能在移动端查看：

- 底部导航或移动端可用导航。
- 事件列表卡片化。
- 事件详情纵向排列。
- 主行动保持可见。

### Design consistency

必须统一：

- 导航。
- 按钮。
- 状态 badge。
- 卡片。
- 空状态。
- 错误状态。
- 表格和移动端列表。
- 图标风格。

### 减少用户思考

产品应主动判断并提示：

- 没有设备时去接入。
- 有待复核事件时去复核。
- 设备离线时去设备详情或接入向导。
- 证据缺失时检查上传队列。
- 系统异常时去健康页。

## 5. 当前功能范围

### 已实现方向

- 工作台。
- 接入向导。
- 复核队列。
- 事件查询。
- Android 事件生成 before/peak/after 三类证据。
- 事件证据复核。
- 复核历史和操作者记录。
- 设备运营中心。
- 设备指标历史和明确排障状态。
- 设备详情。
- 系统健康。
- 设置页基础持久化。
- 后端系统状态接口。
- 后端设备详情接口。
- 后端运行设置接口。

### 后续扩展

- 真实场景证据 before/after 稳定性验证。
- 设备 token。
- 证据保留策略执行和清理任务。
- 更完整的 Android 队列错误原因。
- 实时推送。
- 更完整的 Android 队列可视化。
