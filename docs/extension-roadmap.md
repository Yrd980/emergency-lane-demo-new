# 拓展路线图

## 1. 当前基线

当前系统已经从 demo 骨架升级为产品工作台雏形：

- 有接入向导。
- 有工作台。
- 有复核队列。
- 有事件证据详情。
- 有设备运营中心。
- 有系统健康页。
- 有基本用户反馈。
- 后端能提供系统状态和设备详情。

下一阶段重点不是继续堆页面，而是把长期使用能力做实。

## 2. 优先级 1：证据链完整性

目标：

- 事件详情不只依赖 `frame_peak`。
- 证据链稳定包含进入前、峰值帧、离开后。
- 证据缺失时能说明原因。

建议：

- Android 端缓存触发前后帧。（已完成基础实现）
- 后端保存证据类型和上传状态。
- Web 展示证据完整度和缺失原因。

完成口径：

- 至少 1 条真实 Android 事件含 `frame_before`、`frame_peak`、`frame_after`。
- Web 能按时间顺序展示三类证据。（已完成）
- 缺失证据时页面给出下一步排查建议。

当前状态：

- 自动事件和手动测试事件会尽量生成 `frame_before`、`frame_peak`、`frame_after`。
- 仍需真机验证 before/after 在不同帧率和相机设备上的稳定性。

## 3. 优先级 2：复核工作流

目标：

- 复核人员可以连续处理事件。
- 复核结果可追溯。
- 备注更标准。

建议：

- 复核历史表已完成，后续可继续强化筛选和导出。
- 已记录操作者、复核时间、旧状态、新状态。
- 支持批量复核。
- 支持备注模板维护。

完成口径：

- 复核详情能看到历史。（已完成）
- 改判不会丢失旧记录。（已完成）
- 队列清空后有明确完成状态。

## 4. 优先级 3：设备运营

目标：

- 设备异常能更早暴露。
- 现场人员知道如何恢复。

建议：

- Android 上报更多运行指标：推理耗时、温度等级、存储占用、最近上传错误。
- 后端保存设备指标历史。（已完成基础心跳指标）
- Web 增加设备时间线。（已完成基础指标历史）

完成口径：

- 设备详情能看到最近一段时间状态变化。
- 上传积压能定位到设备，错误原因仍需 Android 队列补充。
- 设备离线能给出明确排障步骤。（已完成）

## 5. 优先级 4：系统治理

目标：

- 本地系统适合更长时间运行。

建议：

- 证据目录保留策略。
- 证据体积统计。
- 设备 token。
- CORS 收紧。
- 配置持久化。

完成口径：

- 设置页配置能保存到后端。
- 证据目录不会无限增长。
- 未授权设备不能随意注册和上传。

当前状态：

- 设置页已经支持基础配置保存到后端。
- 证据目录清理任务、设备 token 校验和 CORS 收紧仍是后续扩展。

## 6. 优先级 5：实时体验

目标：

- 新事件进入时 Web 不依赖手动刷新。

建议：

- 增加 SSE 或 WebSocket。
- 工作台和复核队列收到新事件后自动更新。
- 有新事件 toast。

完成口径：

- Android 上传新事件后，Web 工作台能自动提示。
- 复核队列无需刷新即可出现新事件。

## 7. 不建议现在做

- 自动处罚。
- 执法系统对接。
- 云端多租户。
- 复杂账号体系。
- 大规模并发压测。
- 为了“高级感”重写 Android 检测链路。

## 8. 推荐顺序

1. 证据链补全。
2. 复核历史。
3. 设备指标历史。
4. 证据治理和设备 token。
5. 实时推送。
